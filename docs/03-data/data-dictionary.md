## 2. Key column notes
| Column | Note |
|---|---|
| `game_match.id` | UUIDv7 (time-ordered) generated by Backend, so Match Server and logs can reference it before insert completes and IDs are not enumerable. |
| `match_participant.slot` | `CHECK (slot BETWEEN 1 AND 5)` enforces BR-001 at DB level. |
| `match_participant.loadout_snapshot_json` | Full copy of definitions + stats at match start (FR-024) so balance changes don't rewrite history. |
| `game_match.stake_type` | Only `NONE` allowed now (BR-009); adding a value requires approved design. |
| `room.active_code` | Generated column = `code` while not CLOSED else NULL, with UNIQUE index → codes unique among live rooms while allowing reuse later. |
| `item_definition.stats_json` | JSON until stat schema is decided (OQ-GP-03); promote to columns when stable and queried. |
| `user_account.email` | Nullable until registration method decided; personal data. |

## 3. Integrity rules
- FK constraints everywhere; `ON DELETE RESTRICT` by default (history must not silently disappear). Account deletion is a **pseudonymisation** process, not a cascade (see §5).
- Max 5 competitors: enforced in Backend transaction (`SELECT … FOR UPDATE` on room) + `slot` CHECK + Match Server check (defence in depth, NFR-002).
- One active team leader minimum: enforced in Backend service logic (leader transfer before leaving).
- Exactly one `is_active` loadout per user: enforced in service logic (MySQL lacks partial unique indexes; alternative generated-column trick documented here if needed).
- Result idempotency: `game_match.status` transition `ENDED→COMPLETED` happens once inside a transaction; duplicate reports return the stored result.
- Inventory ownership check for `loadout_slot.inventory_item_id` (same user) in service logic.

## 5. Data lifecycle & retention [P — legal review required, NFR-061]
| Data | Personal? | Retention (proposal) | On account deletion |
|---|---|---|---|
| user_account (username, email, hash) | Yes | Life of account | Erase email/hash; username → `deleted-<id>`; status DELETED after 30-day grace |
| auth_session | Yes (device/IP if logged) | 90 days after expiry | Delete |
| player_profile | Yes | Life of account | Display name pseudonymised |
| inventory, loadouts | Linked | Life of account | Delete |
| match / participants / events | Linked | Indefinite (competitive integrity) | Keep, pseudonymised user reference |
| competitive_record | Linked | Life of account | Delete |
| team membership history | Linked | Indefinite | Pseudonymise |
| report / moderation_action | Yes (sensitive) | 2 years after closure (P) | Keep pseudonymised where needed for safety |
| audit_log | Linked | 2 years (P) | Keep, append-only |
| Server logs (IP addresses) | Yes | 14–30 days | Rotate |
| Live match state (positions, inputs) | No/linked | **Memory only**; discarded at match end | — |

## 6. What stays in memory vs MySQL (Brief §M-13)
| In Match Server memory only | Persisted at end (or on state change) |
|---|---|
| Per-tick physics state, inputs, snapshots, interpolation, peer map, tickets in use | match status transitions, participants, placements, elimination reasons/times, launch summaries, selected events, duration, versions |
| Backend memory only | |
| Match Server registry (instances, state, heartbeats) — rebuilt from re-registration | room/match rows (Backend restart-safe) |
